ISAD — Bach Mai Hospital 🏥

"Design the system before you build it."

Redesigning E-Payment & Appointment Management for Vietnam's Largest Public Hospital

Research Systems Analysis

Bach Mai Hospital is one of Vietnam's largest public hospitals — and its existing payment and appointment process was predominantly manual and fragmented. Patients faced long waiting times, opaque billing, and disconnected steps between booking, consultation, prescription handling, and payment.

This project analyzed the as-is system through stakeholder interviews, then designed a fully integrated digital solution — mobile patient interface, admin portal, MySQL database, and integration with the hospital's existing Health Information System (HIS). The documentation ran to 291+ pages across six formal parts, and every group member received a perfect 10/10 contribution score.

What This Project Was About

Most people who've been to a large public hospital in Vietnam know the experience: take a number, wait, move to another queue, wait again, pay at a separate counter, go back to pharmacy, wait some more. Bach Mai Hospital — one of the country's largest — ran largely on this model. The goal of this project was to design a system that could actually change that.

The core problem

The existing process was fragmented across four disconnected steps: appointment booking, consultation, prescription handling, and payment. None of these steps shared data in real time. Patients had to physically carry paperwork between stations, and staff had to re-enter information that already existed somewhere else in the system.

The proposed solution integrated all four steps into a single digital flow — a mobile-friendly patient interface for booking and managing appointments, an admin portal for hospital staff, a centralized MySQL database, and two-way integration with the hospital's existing Health Information System (HIS) and an SMS/email notification service.

Fact-Finding & Problem Analysis

Before designing anything, the team needed to understand how the current system actually worked — not how it was supposed to work on paper, but how patients and staff actually moved through it day to day.

  • Stakeholder interviews — conversations with hospital staff to document the as-is process and surface pain points that weren't visible from the outside
  • As-is process mapping — current architecture documented and analyzed: where handoffs happened, where information got lost, and where patients spent the most time waiting
  • Business problem statements — each identified gap translated into a clear problem statement with root cause and downstream impact
  • Functional requirements — documented what the to-be system needed to do, separated by actor (patient, HIS, admin, payment gateway)
What the research revealed

The biggest inefficiency wasn't any single step — it was the lack of data continuity between steps. A patient's appointment data didn't automatically flow into their consultation record, which didn't automatically feed into their prescription, which didn't automatically trigger a payment request. Every transition required manual re-entry or physical handoff.

System Design

The project delivered system modeling across six parts, each building on the previous. This wasn't a surface-level design exercise — every diagram had to be technically consistent with every other diagram.

Part 1 — Introduction & Problem Analysis: Business context, stakeholder map, current system architecture, and problem statements.

Part 2 — Fact-Finding & Requirements Modeling: Stakeholder interview findings, as-is BPMN, functional and non-functional requirements.

Part 3 — Data & Process Modeling:

  • BPMN diagrams for the to-be system — patient pool, HIS pool, app system pool, and payment gateway pool
  • Level 0 DFD — system context showing data flows between all external entities
  • Level 1 DFD — detailed breakdown of each major process (appointment, consultation, prescription, payment)

Part 4 — Use Case Modeling: Use case diagrams for each actor with detailed use case descriptions covering main flow, alternative flows, and exception handling.

Part 5 — Object Modeling: Full class diagram with attributes, operations, and relationships between Patient, Appointment, Consultation, Prescription, Payment, and Staff classes.

Part 6 — Database Design & Project Plan: MySQL schema with entity identification, relationship definitions, constraints, and a Work Breakdown Structure (WBS) covering the full implementation roadmap.

291+ pages of documentation

The document ran across six formal submission parts. The volume reflects the depth of analysis required — every use case had to have a matching class, every class had to map to a database table, every process had to have a corresponding BPMN flow. Consistency across the entire system was as important as any individual diagram.

What the Team Delivered

System diagrams:

  • BPMN to-be process maps — patient, HIS, app system, and payment gateway pools
  • Level 0 and Level 1 Data Flow Diagrams
  • Use case diagrams for all actors with complete use case descriptions
  • Full class diagram with attributes, operations, and inter-class relationships

Database design:

  • MySQL schema — entity identification, relationship mapping, and constraint documentation
  • Normalized tables covering patients, appointments, consultations, prescriptions, payments, and hospital staff

UI prototypes:

  • Figma screens for the patient-facing mobile interface — appointment booking, status tracking, payment, and notification flows
  • Admin portal wireframes for hospital staff managing schedules, patient records, and invoices

Project plan:

  • Work Breakdown Structure (WBS) mapping all implementation tasks, dependencies, and estimated effort

My Contribution

  • Fact-finding & requirements modeling — translating stakeholder interview findings into structured functional requirements
  • Data and process modeling — BPMN to-be flows and DFD development (both Level 0 and Level 1)

What I Took Away

"A system design is only as good as its internal consistency. If the use case says it happens, the class diagram needs to support it, and the database needs to store it."

This was the most technically demanding documentation project I'd worked on up to that point. Six parts, 291+ pages, and every diagram had to be consistent with every other diagram. When we caught an inconsistency — a use case referencing an entity that didn't exist in the class diagram, or a DFD process with no corresponding database table — fixing it meant tracing back through multiple documents at once.

The discipline that project taught me: design the data model before designing the interface. It sounds obvious, but every time we started with UI wireframes and worked backward to the data, we ended up with gaps. When we started with the class diagram and worked forward, the interfaces almost designed themselves.

Working on a real-world context (Bach Mai Hospital, a place most Vietnamese people have been to) also made the problem feel concrete in a way that hypothetical projects don't. The pain points we documented weren't abstract — they were things people actually experience.
